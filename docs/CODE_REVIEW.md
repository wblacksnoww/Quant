# Quant Terminal 代码审查报告

> 审查范围：backend/quant（131 个 py 文件，约 23.7k 行）、backend/cpp（约 5.7k 行）、
> gateway/src（约 4.3k 行）、frontend/src（51 个文件，约 20.8k 行）
> 审查方式：通读核心链路 + 编写探针脚本实测验证
> 结论：**工程质量显著高于同类个人量化项目**，问题不在"写得糙"，而在"部分金融假设不够严格"。

---

## 零、先说结论

这个项目的架构判断是对的，而且几处做得比大多数开源量化框架更克制：

- **时序纪律**：`session.py` 的 step 顺序（撮合昨日单 → 收盘重估 → 策略决策 → 日终）把
  "策略在 t 收盘决策、t+1 开盘成交"这条铁律写进了代码结构，而不是靠策略作者自觉。
  `match_on_submit=False` 这个开关的存在说明了作者想清楚过这个问题。
- **记账单一真源**：回测和纸盘共用 `Account.apply_fill`，避免了"回测一套账、实盘一套账"。
- **拒绝静默降级**：`store.py` 明确写了"绝不静默返回空表"，数据降级链有日志。这一条很多人做不到。
- **鉴权无遗漏**：我用 AST 遍历了 102 个路由，没有任何一个漏 `Depends`。这在手写路由的项目里很少见。
- **工程卫生**：`.gitignore` 干净，git 里零构建产物；alembic 迁移、依赖锁、pre-commit 都有。

所以下面的问题我按"会不会让回测结论失真"来排序，而不是按代码风格。

## 一、严重问题（会直接导致回测结论错误）

### 1.1 跳空开盘导致账户负现金（穿仓），无任何校验

**位置**：`backend/quant/execution/broker.py:289-296`（`_estimate_cash`）、
`backend/quant/core/portfolio.py:134`（`apply_fill`）
**C++ 对应**：`backend/cpp/core.cpp:382-387`（`estimate_cash`）、`core.cpp:249`（`cash -= ...`）

冻结资金按"昨收 × 1.02"估算，但市价单实际按**次日开盘价**成交。A 股跳空高开超过 2%
非常常见（一字板打开、隔夜消息）。一旦发生：

```
提交: 9700 股 @ 10 元 → 冻结 98,970.67 元（可用 100,000）
成交: 9700 股 @ 13 元 → cash = -26,139.09 元
```

**实测确认**（探针 A）：

```
提交成功? status=submitted  frozen=98970.67  cash=100000.00
成交后: status=filled  cash=-26139.09  frozen=0.00
>>> cash 为负? True    权益=99960.91
```

`Account.apply_fill` 里 `self.cash -= fill.gross + fill.fees.total` 是**无条件减法**，
没有任何 `if cash < 0` 的分支。C++ 侧 `core.cpp:249` 完全一样。

**为什么严重**：负现金意味着策略用了不存在的杠杆。一次穿仓后，
后续所有权益曲线、收益率、最大回撤全部失真，而且**不会报错**——
回测"成功完成"，只是数字是假的。这类问题最难发现，因为它看起来很正常。

**建议**：
1. 撮合时若 `fill 所需现金 > 可用现金`，按可用现金**缩减成交数量**（部分成交），
   或直接拒单并记录 `BlockReason.INSUFFICIENT_CASH`。真实券商会拒单，不会让你欠钱。
2. `apply_fill` 里加断言 / 记录：`if self.cash < -1e-6: log.error(...)`，
   至少在回测结果里暴露出来，别让用户以为是自己策略牛。
3. 冻结缓冲从固定 2% 改为**可配置**（`gap_buffer_pct`），并在文档里说明这是假设。
4. Python 与 C++ 两处必须同步改，否则等价性测试会挂——这正好是等价性测试该抓的 bug。

### 1.2 前复权数据 + 涨跌停推算，存在假一字板风险

**位置**：`backend/quant/data/base.py:139-148`、`backend/quant/data/providers/akshare_provider.py:172-176`、
`backend/quant/execution/matching.py:70-74`

数据默认 `adjust="qfq"`（前复权），而 `prev_close` 在数据源没给时用
`out["close"].shift(1)` 推算，涨跌停价再由 `prev_close × (1 ± limit_pct)` 计算。

前复权序列内部是自洽的——除权日不会凭空出现 -50%。**但有两个真实风险点**：

1. **混用口径**：如果某天数据源返回了真实 `prev_close`（不复权），而 OHLC 是前复权，
   两者不同口径，就会凭空算出一个"一字跌停"。
2. **除权日的一字板误判**：前复权的做法是把历史价格整体向下缩放。某些数据源的
   qfq 算法在除权日附近 `close/prev_close` 比例不等于 1，此时 `bar.low >= limit_up`
   的判定会失效或误触发。

**为什么严重**：`matching.py:92` 的判定是 `bar.low >= limit_up - 1e-6` → 拒单。
一旦某天被误判为"一字板买不进"，策略当天的信号被静默丢弃，回测收益偏低；
反过来误判为"能成交"，就会在根本买不进的日子里成交，**这个方向的错误会让回测虚高**。

**建议**：
1. 涨跌停价**不要自己推算**，尽量从数据源直接取（东财/腾讯的行情接口有 `涨停价` 字段）。
   `base.py` 的 `COLUMN_ALIASES` 已经认 `涨停价`/`前收盘`，说明链路是通的，只是没优先用。
2. 加一个一致性校验：`abs(close/prev_close - 1) <= limit_pct * 1.5`，
   超出的日子标记为"疑似除权日"，在回测结果里单独列出，让用户能看见。
3. 前复权数据用于**信号计算**是对的，但**成交价与涨跌停**建议用原始价 + 复权因子还原。
   这是行业通行做法，也是回测可信度的分水岭。

### 1.3 GTC 挂单永久冻结资金，且没有任何"挂单寿命"约束

**位置**：`backend/quant/execution/broker.py:251-257`（`end_of_day` 只处理 `TimeInForce.DAY`）

限价单如果永远够不到，`GTC` 会一直挂在 `_live` 里，冻结资金永不释放。

**实测确认**（探针 B）：限价 9.5 买单，市场价一直在 10 以上，10 天后：

```
status=submitted frozen=47514.72 可用现金=52485.28 / 100000.00
```

接近一半的资金被永久锁死，且**策略完全不知道**——`_validate` 只在下单时检查可用现金，
策略会看到"莫名其妙资金不足"的拒单。

**建议**：
1. 加 `max_order_age_days` 配置，超期自动过期（真实券商大多也有 GTC 期限，如 30 天）。
2. 权益快照里已经记了 `frozen_cash`，前端应该把它和"可用现金"一起画出来，
   否则用户看到一个"资金充足却下不了单"的诡异现象。
3. 风控层加一条规则：`frozen / equity > X%` 时告警。

## 二、中等问题（影响可信度或可维护性）

### 2.1 C++ 扩展与 venv 版本不匹配，Python 回退路径"不可见"

**现状**：

```
pyproject.toml requires-python = ">=3.11"
.venv 实际是 Python 3.14.4
已编译产物是 _core.cpython-312-x86_64-linux-gnu.so
→ ImportError: cannot import name '_core'
```

但 `quant/core_native.py` 会捕获导入失败并回退。README 说"没有 Python 回退，
拼装策略缺失扩展时直接报错"——这句和实际行为矛盾。**两种说法必须统一**。

**为什么重要**：我这次审查就是因为跑不了 `_core` 而无法实测 C++ 路径。
用户如果在 3.14 环境里开发，会全程跑 Python 路径（慢 10~70 倍）却浑然不觉，
以为自己在测"加速后的性能"。

**建议**：
1. `core_native.py` 在回退时**打印一条显眼的 warning**（含当前 Python 版本与 `.so` 版本），
   并在 `/api/system/info` 里暴露 `native_available: false` + 原因。前端应该能看到这个状态。
2. CI 里加一个矩阵：3.11/3.12/3.13 都编译一次，避免版本漂移。
3. `requires-python` 收紧到实际验证过的范围（如 `>=3.11,<3.14`），别声称支持没测过的版本。

### 2.2 缺少参数寻优与 walk-forward，这是量化平台的"核心闭环缺口"

我 grep 了全仓库：**没有** `optimize` / `grid_search` / `walk_forward` 任何一种实现。

现状是：用户调参数 → 看一个回测结果 → 再调 → 再看。这个循环**天生会过拟合**，
因为没有任何机制告诉用户"你这个夏普 2.5 是在 200 组参数里挑出来的最好的那组"。

**建议**（按投入产出排序）：
1. **最小可用版**：参数网格 + 并发回测 + 结果表格（按夏普/卡玛排序）。
   现有 `BacktestManager` 持久化队列已经能支撑，工作量不大。
2. **真正有用版**：walk-forward 切分（滚动训练窗/测试窗），输出样本内 vs 样本外
   的指标对比图。这一张图能救很多人的策略。
3. **防御性提示**：回测结果页显示"本次运行搜索了 N 组参数"，
   超过 50 组时给出过拟合警告。这是成本最低、价值最高的一条。

### 2.3 基准对比过于简陋

**位置**：`backend/quant/metrics/performance.py:244-249`

```python
report.benchmark_return = bench.iloc[-1] / bench.iloc[0] - 1.0
report.excess_return = report.total_return - report.benchmark_return
```

只有"区间总收益之差"，没有：
- **年化**超额（区间长短不同没法比）
- **Beta / Alpha**（策略到底是在赚市场还是赚选股）
- **信息比率**（超额收益的稳定性）
- **跟踪误差**

`excess_return` 用算术相减而非几何，长区间会失真（10 年 200% vs 100%，
真实超额是 50%，算术差是 100%）。

**建议**：至少补 Beta/Alpha 和年化超额。Beta 尤其重要——如果一个策略 Beta=1.2、
Alpha=0，它根本不是"策略"，就是加杠杆买指数。

### 2.4 撮合的成交价假设偏乐观

`matching.py:104-105`：市价单按 `bar.open` 成交，无任何冲击成本。

对日线策略可以接受，但：
- 大资金/小盘股，`bar.open` 是开盘集合竞价的边际价格，你的单子进去会推高价格
- `volume_limit_pct=0.10` 限制的是**单根 bar 的成交量占比**，但成交价仍按 `open`，
  即"吃掉 10% 的成交量却不影响价格"，逻辑上不自洽

**建议**：加一个"量价冲击"模型：`price_impact = k * sqrt(participation_rate)`。
哪怕 k 取一个保守经验值，也比假设零冲击诚实。这是回测可信度的重要一环。

### 2.5 幸存者偏差：没有历史成分股支持

grep 确认没有 `universe` / 历史成分股概念。用户如果拿"今天沪深 300 的成分股"
回测 2015 年，会得到系统性偏高的收益——2015 年至今被剔除的 100 多只票
（大多是跌得惨的）全部不在样本里。

**建议**：
1. 短期：在回测提交页显著提示"股票池为静态名单，存在幸存者偏差"。
2. 中期：支持"按日期查询成分股"，数据源（akshare 有 `index_stock_cons` 历史接口）能拿到。

### 2.6 137 处 `except Exception`，其中不少是"吞掉后继续"

```bash
grep -c "except Exception" → 137 处，134 处带 noqa: BLE001
```

B001 被大面积豁免，意味着"吞异常"成了默认风格。大部分地方有 `log.exception`，
处理是得当的（比如风控规则异常按拒单处理，这个决策是对的）。
但有几类值得收紧：

- `risk/base.py:400`：规则异常 → 拒单。合理，但应该区分"规则 bug"与"数据问题"，
  前者应该告警到前端，而不是静默变成拒单率。
- `session.py:170`：旧策略 `on_stop` 异常被吞。策略切换时如果 `on_stop` 崩了，
  可能留下未清理的状态，应该至少上报到事件流。

**建议**：不用改 137 处。挑 5~10 处"吞掉后行为发生实质变化"的地方收紧即可。
在 ruff 配置里对 `except Exception` 加一条"必须同时有 log 或 raise"的约定。

### 2.7 `schemas.py` 821 行，单文件过大

所有 Pydantic 模型集中在一个文件。配合前端 `api/schema.ts` 已有 6315 行
（自动生成，可接受），后端手写模型也该拆了。

**建议**：按域拆成 `schemas/{auth,market,backtest,paper,live,strategy,fund}.py`，
`__init__.py` 重新导出。改动机械但收益明显（多人协作时的 merge 冲突会少很多）。

## 三、轻微问题

### 3.1 `metrics` 在极短区间产生离谱年化

**实测确认**（探针 5）：

```
 2 点: annual=164238.7707   ← 16 万倍年化
 3 点: annual=2998.0628
10 点: annual=10.0432       ← 1000%
```

公式 `(final/start)**(1/years) - 1`，其中 `years = len(series)/252`。
2 个数据点 → `years ≈ 0.0079`，年化被放大 126 倍。

**建议**：`years < 5/252`（不足 5 个交易日）时 `annual_return = NaN` 或直接返回总收益，
前端显示"区间过短，年化无意义"。

### 3.2 `profit_factor` 用 999.0 代替 inf

`performance.py:231`：`report.profit_factor = pf if np.isfinite(pf) else 999.0`

999 是一个魔数，前端会当成真实值排序。**建议**前端显示"∞"或"无可比亏损"，
API 返回 `null`。

### 3.3 `slippage_bps` 默认 0.0

**位置**：`cost.py:38`

默认零滑点意味着"策略永远按理论价成交"。回测默认参数应该是**保守**的，
不是**乐观**的。建议 A 股默认 5bp、小盘股 10bp，至少在 UI 上强制用户看一眼。

### 3.4 `max_position_pct` 默认 0.98

**位置**：`risk/base.py:310`。注释解释了理由（"不替用户决定仓位"），
逻辑说得通。但 0.98 意味着"几乎不设防"，而叫"单票仓位上限"会让人误会它有保护作用。
**建议**改名为 `max_position_guard`（守卫而非限制），或默认调到 0.5。

### 3.5 前端无统一状态管理

21 个文件里散落 `useState`，没有 Context/Store。轮询逻辑（1s/3s/5s）
在 `Market.tsx`(5 处 useEffect)、`Instrument.tsx`(9 处) 里各自实现。

**风险**：页面切换后如果清理不干净，会有多个轮询同时在跑打后端。
**建议**：抽一个 `usePolling(fn, interval, deps)` hook 统一管理，
自动处理 cleanup 和页面可见性（`document.hidden` 时暂停，省流量也省后端）。

### 3.6 单文件组件偏大

`Settings.tsx` 1090 行、`Instrument.tsx` 802 行、`Market.tsx` 756 行。
**建议**：Settings 按 Tab 拆，Instrument 把"K线区/规则表/策略启动"拆成三个子组件。

## 四、架构层面的判断（这条可能是最重要的）

### 4.1 C++ 双实现的复杂度，正在压过它的收益

现状：
- `backend/cpp/` 5.7k 行，实现撮合、账本、指标、策略解释器、主循环
- Python 侧有**同一套逻辑**的独立实现
- `test_native_equivalence.py` 用 8 个测试点把门

**这是用"两倍代码 + 等价性测试"换 10~70 倍回测速度。** 值得吗？分情况：

- **值得**：如果你要跑参数网格（几百次回测）或分钟级高频回测。Python 跑 500 次
  日线回测可能要几小时，C++ 十几分钟——这个差距是质变。
- **不值得**：如果只是偶尔跑一次日线回测。Python 跑 3 年日线在 1000 个标的上
  可能也就 30 秒，用户完全能等。

**但真正的成本不是性能，是第二个 bug 面**：我上面找到的负现金 bug，
Python 和 C++ **各有一份**，而且必须同时修两次。今天它还能被等价性测试抓到
（因为两边行为一致地错），但哪天有人只修了一边，等价性测试会挂——
然后最容易的"修复"是把测试改成容忍差异。这是双实现架构的经典腐化路径。

**建议**：
1. **不要扩 C++ 范围**。现在 C++ 只覆盖回测热路径，边界划得很合理。
   `news_dual_ma` 和带 benchmark 的回测留在 Python 是对的，**别再往 C++ 搬**。
2. **等价性测试要从"结果一致"升级到"语义正确"**。现在的测试是
   "Python 输出 == C++ 输出"，但两边都错时测试照样通过。
   应该补独立的"物理正确性"测试：比如"现金永不为负"、"成交股数 ≤ bar 成交量"、
   "同一天买卖不超过可用股数"。这类不变量测试比等价性测试值钱得多。
3. 性能上还有个更便宜的方向：Python 路径用的是逐 bar 循环 + 逐行 `bar_from_frame`
   （`session.py:51-69` 每次都 `frame.iloc[index]` 取 Series）。如果 Python 路径
   改成 numpy 列式访问，可能能快 5~10 倍，**不需要维护第二份 C++ 逻辑**。
   这条路值得先试，再决定 C++ 要不要继续投。

### 4.2 值得称道的一点：`TradingSession` 的抽象是对的

`session.py` 让回测/纸盘/实盘共用同一个 `step()`，差异只在
`auto_end_of_day`、`SimClock` vs `RealClock`、`match_on_submit`。
这个抽象**没有为了统一而过度统一**——它没有试图把"交易所回报驱动"（实盘）
硬塞进"轮询驱动"（回测），而是在 `step()` 里用注释明确了这个边界
（`session.py:211`："实盘由交易所回报驱动"）。

这是很成熟的设计判断。**别动它。**

## 五、建议的修复顺序

| 优先级 | 事项 | 理由 | 预估投入 |
|---|---|---|---|
| P0 | 负现金（穿仓）校验 + 部分成交缩减 | 直接导致回测结论错误，且静默 | 中（Python+C++ 双改） |
| P0 | 涨跌停价优先用数据源真值 + 除权日标记 | 假一字板让回测虚高或虚低 | 中 |
| P1 | GTC 挂单寿命 + 前端展示冻结资金 | 资金被锁死，用户无法理解 | 小 |
| P1 | `native_available` 状态暴露 + 显式告警 | 用户可能在不知情下跑慢路径 | 小 |
| P1 | 补 Beta/Alpha/年化超额 | 现在是"策略还是 beta"都分不清 | 小 |
| P2 | 参数寻优 + walk-forward | 平台的**研究闭环**缺口，决定这工具是否真能做研究 | 大 |

## 六、一句话总评

**这是一个"骨架很对、器官齐全、但病理切片还有几处没看完"的项目。**

架构、时序纪律、记账单一真源、鉴权覆盖这些"地基"做得比大部分同类项目好，
README 里那句"一套撮合与会话代码同时服务回测、纸盘和实盘"是**真的做到了**，
不是营销话术——我从 `session.py` 和 `SimBroker` 的复用方式确认了这一点。

真正该补的不是更多功能（市场、策略、蓝图已经够多了），而是
**让回测结论可信的那几道防线**：负现金校验、涨跌停真值、参数寻优的过拟合防护。
这三件事做完，这个项目才从"很酷的量化终端"变成"能用来做真实研究的工具"。
